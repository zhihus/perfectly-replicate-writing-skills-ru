# Интеграция OpenSpec и скилла `perfectly-replicate-writing-skills-ru`

> Аналитический документ. Не содержит кода интеграции и не вносит изменений в файлы скилла.
> Дата: 2026-11-10. Основано на реальном содержимом скилла (`SKILL.md`, `references/`, `.audit/style-card-raitek.md`) и реальных OpenSpec-проектов (`Manifest/openspec`, `InvestPlan/openspec`).

---

## 1. Резюме

**Совместимость: высокая.** OpenSpec и скилл не конкурируют, а дополняют друг друга, потому что они отвечают за две **ортогональные оси** одного документа:

- **OpenSpec = WHAT** — *что* должно быть в ТЗ: факты, требования, логика, структура разделов, сценарии поведения (WHEN/THEN).
- **Скилл = HOW** — *как* это должно быть написано: лексика, тон, стилевые маркеры, пунктуационный fingerprint, «пищевые гены» (writing genes) автора.

Ключевой вывод: **`spec.md` из OpenSpec становится *контент-брифом*, а Style Card из скилла — *стилевой связкой*.** Скилл уже умеет генерировать текст в стиле (Фаза 4 Blind Test генерирует тестовые тексты по 500–700 слов), но у него **нет входного режима «сгенерировать документ из готового контент-спека»**. Это единственное, что нужно добавить в связку — и это не изменение логики скилла, а новый тип входных данных.

**Степень готовности: 8/10.** Оба инструмента уже работают, оба говорят на Markdown, оба имеют механическую валидацию (`openspec validate` для спека, Blind Test с порогом 70% для стиля). Главная работа — не «написать код», а **согласовать интерфейсы**: какой именно артефакт OpenSpec передавать скиллу, в каком порядке, и как организовать двойную валидацию на выходе.

**Главный риск:** переполнение контекста. OpenSpec-спеки могут быть объёмными (несколько capabilities, десятки сценариев), а Style Card — компактной карточкой. Если скормить скиллу весь change целиком, стилевые маркеры «утонут» в потоке требований. Решение — **секционная подача** (по одному capability / по одной волне), что уже заложено в самой философии OpenSpec («корми исполнителя только текущей задачей, а не всем change»).

## 2. Схема интеграции

Ниже — полный workflow создания нового ТЗ с участием пользователя, OpenSpec и Скилла.

### 2.1. Участники

| Роль | Что делает |
|------|-----------|
| **Пользователь** | Формулирует бизнес-задачу, запускает OpenSpec propose, затем запускает Скилл, принимает результат |
| **OpenSpec** | Формирует и хранит требования (spec.md, proposal.md, design.md, tasks.md), валидирует их механически |
| **Скилл** | Принимает контент-спека + Style Card и генерирует ТЗ в стиле автора, валидирует стиль |

### 2.2. Пошаговый workflow

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  ШАГ 1. БРИФ (пользователь)                                                │
│  Пользователь описывает бизнес-задачу: «нужно ТЗ на модуль X для 1С:ERP»   │
└──────────────────────────────┬──────────────────────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  ШАГ 2. OPENSPEC PROPOSE                                                   │
│  Команда: /openspec-propose  (или «openspec propose»)                       │
│  OpenSpec создаёт openspec/changes/<name>/:                                │
│    • proposal.md   — Why / What Changes / Capabilities / Impact             │
│    • specs/<cap>/spec.md — ADDED/MODIFIED Requirements + Scenarios (WHEN/THEN)│
│    • design.md     — Context / Goals / Decisions / Risks / Migration        │
│    • tasks.md      — FR N.M, волны, stop-criteria                           │
│    • .openspec.yaml— schema + created                                       │
└──────────────────────────────┬──────────────────────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  ШАГ 3. ВАЛИДАЦИЯ СПЕКА (OpenSpec, механическая)                            │
│  Команда: openspec validate --change "<name>"                               │
│  Проверяет: структура spec.md, наличие WHEN/THEN, соответствие proposal.    │
│  Если есть ошибки — правим спека и повторяем.                               │
│  ✔ Spec готов: это наш КОНТЕНТ-БРИФ (WHAT).                                 │
└──────────────────────────────┬──────────────────────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  ШАГ 4. ГЕНЕРАЦИЯ ТЗ (Скилл)                                               │
│  Команда-триггер (см. 2.3). Скилл берёт:                                    │
│    • контент-бриф = specs/<cap>/spec.md (+ proposal.md как контекст)        │
│    • Style Card  = .audit/style-card-<author>.md                            │
│  И генерирует ТЗ: содержание из спека, стиль из Style Card.                 │
└──────────────────────────────┬──────────────────────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  ШАГ 5. ДВОЙНАЯ ВАЛИДАЦИЯ                                                  │
│  (A) SPEC COMPLIANCE — сверка ТЗ со спеком:                                 │
│      все ли Requirements из spec.md покрыты разделами/пунктами ТЗ?          │
│      все ли Scenarios (WHEN/THEN) отражены в сценариях ТЗ?                  │
│  (B) STYLE COMPLIANCE — Blind Test скилла:                                  │
│      сгенерированный фрагмент ТЗ сверяется с оригиналом автора по 7+1       │
│      измерениям; композитное совпадение должно быть ≥70%.                   │
│  Если (A) или (B) не пройдены — правим и повторяем ШАГ 4.                   │

                               │
                               ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  ШАГ 6. ФИНАЛИЗАЦИЯ                                                        │
│  • ТЗ сохраняется как артефакт проекта.                                     │
│  • OpenSpec: openspec archive --change "<name>" (change → archive/).        │
│  • Скилл: если автор «показал себя» иначе — инкрементальное обновление      │
```

### 2.3. Конкретная команда-триггер (как пользователь просит скилл)

Это **критически важная** часть — именно так пользователь запускает связку на практике.

**Базовый формат:**

```
Сгенерируй ТЗ из спеки <путь-к-spec.md>, используя Style Card <путь-к-style-card.md>
```

**Примеры реальных команд:**

```
Сгенерируй ТЗ из спеки openspec/changes/add-structure-parser/specs/structure-parser/spec.md,
используя Style Card .audit/style-card-raitek.md
```

```
Сгенерируй ТЗ из спеки openspec/changes/add-verify-script/specs/verify-script/spec.md,
используя Style Card .audit/style-card-raitek.md,
формат — бизнес-ТЗ 1С, разделы — по структуре спека
```

**Что делает скилл при такой команде:**
1. Читает `spec.md` как **контент-бриф**: извлекает Requirements (что должно быть) и Scenarios (WHEN/THEN → сценарии ТЗ).
2. Читает `style-card-*.md` как **стилевую связку**: применяет лексические маркеры, пунктуационный fingerprint, «пищевые гены», запрещённый список.
3. Генерирует ТЗ: **содержание** строго из спека, **стиль** строго из Style Card.
4. Выполняет двойную валидацию (spec compliance + style compliance).

**Важно:** эта команда **не требует изменения SKILL.md**. Она использует уже существующую способность скилла генерировать текст (Фаза 4), просто с новым типом входных данных — готовым контент-спеком вместо «напиши что-то в этом стиле». Единственное, что нужно формализовать, — *правило маппинга* «Requirement → раздел ТЗ, Scenario → сценарий ТЗ» (см. раздел 3).

### 2.4. Вариант «в одну кучу» (упрощённый, для мелких ТЗ)

Для небольших изменений (1 capability, < 10 сценариев) можно объединить шаги:

```
Сгенерируй ТЗ из change <name> (openspec/changes/<name>/),
используя Style Card <путь>. Контент бери из spec.md + proposal.md,
стиль — из Style Card.
```

Для объёмных изменений (несколько capabilities) **обязательна секционная подача** — см. раздел 5, риск «переполнение контекста».

## 3. Анализ интерфейсов

### 3.1. Что OpenSpec отдаёт скиллу (форматы)

OpenSpec хранит артефакты в `openspec/changes/<name>/`. Для генерации ТЗ скиллу нужны **только два файла**:

| Файл | Роль в связке | Что скилл берёт |
|------|--------------|-----------------|
| `specs/<capability>/spec.md` | **Контент-бриф (основной вход)** | Requirements (ADDED/MODIFIED) → разделы ТЗ; Scenarios (WHEN/THEN) → сценарии ТЗ |
| `proposal.md` | Контекст (опционально) | Why / What Changes — для понимания «зачем», помогает скиллу выстроить вступление ТЗ |

Остальные артефакты скиллу **не нужны**:
- `design.md` — это *как реализовать* (для разработчика), не *что описать в ТЗ*.
- `tasks.md` — это *план работ* (для исполнителя), не *содержание документа*.
- `.openspec.yaml`, `config.yaml` — служебные метаданные, не контент.

### 3.2. Структура `spec.md` → маппинг на ТЗ

Реальный пример из `Manifest/openspec/changes/add-structure-parser/specs/structure-parser/spec.md`:

```markdown
# Spec Delta

## Purpose
The structure-parser capability mechanically validates ...

## ADDED Requirements

### Requirement: CLI invocation and exit codes
The parser MUST accept exactly one Markdown file path ...

#### Scenario: clean reference file
- **WHEN** the parser runs with a fully compliant document ...
- **THEN** the process exits with code 0 ...
```

**Правило маппинга (что нужно формализовать в связке):**

| Элемент spec.md | Элемент ТЗ |
|-----------------|------------|
| `## Purpose` | Введение / цель ТЗ |
| `### Requirement: <name>` | Раздел ТЗ (описание функции/поведения) |
| `#### Scenario: <name>` + WHEN/THEN | Сценарий использования в ТЗ («При ... происходит ...») |
| `MUST` / `SHALL` | Обязательные требования (жирным / в разделе «Требования») |

**Ключевой момент:** скилл **не переписывает** логику спека — он лишь *переводит* её в формат бизнес-ТЗ 1С и *одевает* в стиль автора. Факты и логика остаются нетронутыми (это зона ответственности OpenSpec, см. раздел 4).

### 3.3. Что скилл отдаёт (Style Card как вход)

Style Card — это компактная Markdown-карточка (пример: `.audit/style-card-raitek.md`, ~322 строки в `examples/抓马教育-style/style-card.md`). Она содержит:

- **Метаданные** — автор, платформа, жанр, статистика корпуса.
- **7 измерений** — лексика, синтаксис, тональность, дискурс, риторика, эмоция, перспектива (по 3–5 выводов каждое).
- **Пищевые гены** (writing genes) — 3–5 кросс-валидированных признаков.
- **Запрещённый список** — 5–10 пунктов «автор никогда не делает».
- **Адаптация к формату** — таблица «формат → уровень соответствия».

**Размер Style Card** — это ключевое преимущество для контекста: она компактна (порядка 3–5 тыс. слов), в отличие от OpenSpec-спека, который может быть в десятки раз больше. Поэтому Style Card **всегда помещается** в контекстное окно, а спека — нет (см. раздел 5).

### 3.4. Формат передачи данных: Markdown → Markdown

Оба инструмента работают с **Markdown**, поэтому handoff естественный — никаких конвертеров не нужно. Скилл просто читает `spec.md` как обычный Markdown-файл. Единственное, что нужно — **согласовать, какой именно артефакт** передавать (ответ: `spec.md` + опционально `proposal.md`).

### 3.5. Чего сейчас нет в скилле (разрыв интерфейса)

Скилл принимает входные данные «напрямую: вставкой, путями к файлам, контекстом разговора» (SKILL.md Phase 0). Но его вход — это **корпус текстов автора** (для анализа стиля), а **не контент-спека** (для генерации по брифу). Это разные типы входа:

- **Существующий вход:** «Вот N статей автора — проанализируй их стиль» → Style Card.
- **Нужный вход:** «Вот контент-спека + Style Card — сгенерируй ТЗ» → ТЗ.

Второй вход **не требует изменения фаз анализа** (Phase 0–2), потому что Style Card уже готова. Он использует только **способность генерации** (Phase 4) + **правило маппинга** (раздел 3.2). Это и есть «новый режим входа», упомянутый в резюме.

## 4. Матрица ответственности

| Аспект | OpenSpec (WHAT) | Скилл (HOW) |
|--------|-----------------|-------------|
| **Факты и логика** | ✅ Владеет: что система должна делать, требования, сценарии | ❌ Не трогает: не изобретает и не меняет факты |
| **Структура требований** | ✅ Владеет: разделы, иерархия Requirements/Scenarios | ⚠️ Адаптирует: переносит структуру в формат бизнес-ТЗ 1С (нумерация, заголовки) |
| **Валидация содержания** | ✅ `openspec validate` — механическая проверка спека | ❌ Не отвечает |
| **Лексика** | ❌ Не отвечает | ✅ Владеет: фингерпринт-слова, коллокации, термины |
| **Тон и регистр** | ❌ Не отвечает | ✅ Владеет: формальность, разговорность, эмоциональная температура |
| **Стилевые маркеры** | ❌ Не отвечает | ✅ Владеет: пунктуационный fingerprint, «Рисунок - N», ЗАКАЗЧИК/ИСПОЛНИТЕЛЬ, choppy-фразы |
| **Валидация стиля** | ❌ Не отвечает | ✅ Blind Test: композитное совпадение ≥70% |
| **Версионирование требований** | ✅ `changes/` → `archive/`, spec deltas | ❌ Не отвечает |
| **Версионирование стиля** | ❌ Не отвечает | ✅ Инкрементальное обновление Style Card (delta-analysis) |
| **Хранение артефактов** | ✅ `openspec/` | ✅ Style Card в `.audit/` или persona-подскилл |

### 4.1. Зона пересечения: структура ТЗ

Единственное место, где ответственности **пересекаются**, — **структура документа** (разделы, нумерация, заголовки). Здесь важно правило **«не мешать»**:

- **OpenSpec определяет *логическую* структуру** (какие Requirements, в каком порядке).
- **Скилл определяет *формальную* структуру** (как эти разделы выглядят в бизнес-ТЗ 1С: нумерация `1.`, `1.1.`, шапка «УТВЕРЖДАЮ», оглавление).

**Правило «не мешать»:**
1. Скилл **не добавляет** Requirements, которых нет в спеке.
2. Скилл **не убирает** Requirements из спека.
3. Скилл **не переписывает** логику WHEN/THEN — только переводит её в язык ТЗ.
4. Если в спеке есть элемент, который «не вписывается» в стиль автора (например, слишком длинное предложение против choppy-фраз 8–15 слов) — скилл **разбивает** его на короткие предложения, **не меняя смысла**.

### 4.2. Как они не мешают друг другу

- **OpenSpec не знает о стиле.** Он валидирует спека по своей схеме (структура, WHEN/THEN) и не смотрит на лексику.
- **Скилл не знает о требованиях.** Он не проверяет, полные ли требования, — только то, что *написанное* соответствует стилю и что *содержание* покрыто спеком (spec compliance в ШАГ 5A).
- **Разделение чистое:** OpenSpec отвечает на вопрос «что должно быть?», скилл — «как это должно выглядеть?». Ни один не вторгается в зону другого.

## 5. Выявленные риски и способы их минимизации

### Риск 1. Переполнение контекста (критический)

**Суть:** OpenSpec-спеки могут быть объёмными (несколько capabilities, десятки сценариев, сотни строк). Если скормить скиллу весь change целиком, стилевые маркеры из компактной Style Card «утонут» в потоке требований — модель начнёт «забывать» стиль и писать нейтрально.

**Минимизация:**
- **Секционная подача.** Генерировать ТЗ не целиком, а **по одному capability** (или по одной волне tasks.md). Это уже заложено в философии OpenSpec: «корми исполнителя только текущей задачей, а не всем change».
- **Style Card всегда в контексте.** Она компактна (3–5 тыс. слов) и **всегда** помещается — её нужно держать «рядом» с каждым секционным брифом.
- **Лимиты OpenSpec уже помогают.** В `config.yaml` проекта Manifest заданы лимиты: задача > 6000 символов — разбивать. Это означает, что и spec.md, и tasks.md уже нарезаны на управляемые куски, которые удобно подавать скиллу по одному.

### Риск 2. Конфликт Markdown-диалектов

**Суть:** OpenSpec использует свой диалект Markdown (`# Spec Delta`, `### Requirement:`, `#### Scenario:`, `WHEN/THEN`), а бизнес-ТЗ 1С — свой (шапка «УТВЕРЖДАЮ», нумерация `1.` → `1.1.`, «Рисунок - N» с дефисом, «ЗАКАЗЧИК/ИСПОЛНИТЕЛЬ»). Если скилл просто скопирует заголовки спека, получится «гибрид», который не похож ни на спека, ни на ТЗ.

**Минимизация:**
- **Правило маппинга** (раздел 3.2) явно определяет, как каждый элемент spec.md превращается в элемент ТЗ. Заголовки `### Requirement:` **не переносятся** как есть — они становятся нумерованными разделами ТЗ.
- **Style Card содержит «формат адаптацию»** — таблица «формат → уровень соответствия». Для формата «бизнес-ТЗ 1С» она уже описана в `references/7-dimensions-framework.md` (маркеры 1С). Скилл применяет именно её, а не заголовки спека.

### Риск 3. Конфликт метаданных

**Суть:** OpenSpec хранит метаданные в `config.yaml` и `.openspec.yaml` (schema, created, rules). Скилл хранит метаданные автора в Style Card (автор, платформа, жанр, статистика корпуса). Это разные метаданные, и если их смешать, возникнет путаница.

**Минимизация:**
- **Не смешивать.** Метаданные OpenSpec (schema, created) — это *служебные* данные фреймворка, они **не передаются** скиллу. Скилл берёт только *контент* (spec.md, proposal.md) и *свои* метаданные (Style Card).
- **Явное разделение в команде-триггере:** «контент бери из spec.md, стиль — из Style Card» — метаданные OpenSpec в команду не входят.

### Риск 4. Версионирование: changes/archive vs инкрементальные обновления Style Card

**Суть:** OpenSpec версионирует требования через `changes/` → `archive/` (каждое изменение — отдельный change, после реализации архивируется). Скилл версионирует стиль через **инкрементальные обновления** Style Card (delta-analysis на новых документах, SKILL.md Phase 0 «Updating Existing Clone»). Это две разные модели версионирования, и они могут рассинхронизироваться: ТЗ сгенерировано по старой Style Card, а автор уже «показал себя» иначе.

**Минимизация:**
- **Связать версии.** В команде-триггере указывать **конкретную версию Style Card** (например, по дате или хэшу), чтобы ТЗ всегда генерировалось по известному состоянию стиля.
- **Перегенерация.** Если Style Card обновлена, ТЗ, сгенерированные по старой версии, можно **перегенерировать** по новой — контент-спека не меняется, меняется только стиль. Это дёшево, потому что OpenSpec-артефакты (spec.md) не трогаются.
- **Архивация OpenSpec не влияет на Style Card.** Архивация change — это про *требования*, а не про *стиль*. Стиль живёт в своём цикле (Style Card), требования — в своём (changes/archive).

### Риск 5. Смешение языков

**Суть:** Артефакты OpenSpec в реальных проектах (`Manifest`, `InvestPlan`) написаны **на английском** (proposal.md, spec.md, design.md, tasks.md — все на английском). Скилл генерирует вывод **на языке автора** (для русскоязычного автора 1С — на русском). Если скилл получит англоязычный спека, он должен **перевести** его на русский, сохранив факты.

**Минимизация:**
- **Явное указание языка в команде-триггере:** «Сгенерируй ТЗ ... на русском, в стиле автора». Скилл и так генерирует на языке автора (Style Card), но явное указание снимает неоднозначность.
- **Перевод без потери фактов.** Скилл переводит спека на русский, но **не меняет** логику WHEN/THEN и требования. Это зона ответственности OpenSpec (факты), скилл только *переводит*, не *переосмысляет*.
- **Альтернатива:** писать OpenSpec-спеки сразу на русском (в `config.yaml` можно задать правила на русском, как в `Manifest/openspec-rules.md`). Тогда перевод не нужен.

### Риск 6. Дрейф стиля при жёсткой структуре спека

**Суть:** Бизнес-ТЗ 1С — это **жёсткий** формат (шапка, нумерация, стандартные конструкции «При нажатии на кнопку X ...»). Если спека задаёт структуру, которая «конфликтует» со стилем автора (например, автор пишет choppy-фразы 8–15 слов, а спека требует длинные сложные предложения), скилл может «задавить» стиль структурой или наоборот — «сломать» структуру стилем.

**Минимизация:**
- **Приоритет структуры.** Формальная структура ТЗ (шапка, нумерация, разделы) **непререкаема** — она определяется жанром «бизнес-ТЗ 1С», а не стилем автора. Стиль применяется *внутри* этой структуры (лексика, тон, длина предложений), но не ломает её.
- **Blind Test как контроль.** Если после генерации композитное совпадение < 70% (SKILL.md Phase 4 Quality Gate), скилл **флагирует** расхождение и предлагает пересмотреть. Это защита от дрейфа.
- **Запрещённый список Style Card** — дополнительная защита: если скилл «хочет» написать то, что автор «никогда не делает», запрещённый список его останавливает.

### Риск 7. Дублирование функций (архитектурный конфликт)

**Суть:** OpenSpec уже содержит `design.md` (как реализовать) и `tasks.md` (план работ). Скилл генерирует ТЗ (что реализовать). Если ТЗ и design.md начнут дублировать друг друга, возникнет путаница: где «источник правды» для содержания?

**Минимизация:**
- **Разделить по назначению.** `design.md` — это *для разработчика* (архитектура, решения, компромиссы). ТЗ — это *для заказчика* (что должно быть, сценарии, требования). Они **не дублируют** друг друга, а **дополняют**: ТЗ отвечает «что», design.md — «как».
- **Единый источник правды для содержания.** Содержание ТЗ берётся **только** из `spec.md` (Requirements/Scenarios), а не из `design.md`. Если в design.md есть деталь, которой нет в spec.md — она **не попадает** в ТЗ (это зона ответственности OpenSpec, и он сам решает, что выносить в спека).

## 6. Итоговая рекомендация

**Связка OpenSpec + Скилл работает и не требует изменения файлов скилла.** Для её запуска нужно:

1. **Согласовать интерфейс:** скилл берёт `spec.md` (+ опционально `proposal.md`) как контент-бриф и Style Card как стилевую связку.
2. **Формализовать правило маппинга** «Requirement → раздел ТЗ, Scenario → сценарий ТЗ» (раздел 3.2) — это не код, а *документированная конвенция*.
3. **Ввести команду-триггер** (раздел 2.3) как стандартный способ запуска: «Сгенерируй ТЗ из спеки X, используя Style Card Y».
4. **Организовать двойную валидацию** (spec compliance + style compliance) как обязательный шаг перед финализацией.
5. **Секционная подача** для объёмных спеков (по capability / по волне) — защита от переполнения контекста.

**Главный принцип:** OpenSpec отвечает на вопрос **«что должно быть?»**, скилл — на вопрос **«как это должно выглядеть?»**. Ни один не вторгается в зону другого, и вместе они дают полный документ: ТЗ с правильным содержанием (от OpenSpec) и в правильном стиле (от скилла).
